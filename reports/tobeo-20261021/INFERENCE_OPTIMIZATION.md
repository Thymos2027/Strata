# 推理优化选题：本机证据、上游已有工作与贡献路线

研究日期：2026-10-21。目标是做有因果证据的推理优化贡献，能解释瓶颈、实现、实验和取舍。本文是代码与讨论调研，加一项本机功能探针；未实现或测量的方案均不是性能承诺。

## 优先选择

建议先做 **混合核 CPU 的端到端亲和性校准**，再研究 **多会话切换时的 RAM 缓存成本**。前者已有本机收益证据、实现范围较小；后者更贴近 Agent 服务与内存调度，有机会做成更深入的系统优化案例。CUDA/AVX2 算子优化作为第三阶段，先定位再动代码。

| 方向 | 本机证据 | 潜在 PR 内容 | 求职展示重点 | 当前结论 |
| --- | --- | --- | --- | --- |
| 端到端亲和性校准 | 固定实际缓存后的 P 核解码中位数收益 7.2% / 12.2% / 8.0% | 现有校准器比较实际布局、交替确认并保存结果 | 异构 CPU 调度、实验设计、产品化 | 最适合先落地；已有收益不等于新补丁收益 |
| 多会话 RAM 缓存 | 连续相同请求命中，插入另一会话后回访不命中 | 先补交错会话基准；确认瓶颈后改善现有停车策略或诊断 | 推理服务、缓存、状态管理、延迟/内存取舍 | 值得主攻，但尚未证明存在需要修复的缺陷 |
| PLE 读路径 | 128 GB RAM 有余量；SSD 初始化探测约 289K rows/s | 测量批量去重、并发深度或复用；不重复已有 RAM 模式 | Windows 异步 I/O、数据局部性 | 先分解长提示耗时，不保证收益 |
| AVX2 IQ3_S 专家内核 | CPU 支持 AVX2；现有 exact1 优化已上游实现 | 针对 profile 中占比高的具体行解码/点积路径 | SIMD、量化、数值一致性、Roofline | 技术含量高，但当前没有新瓶颈证据 |
| sm_120 CUDA 内核 | GPU 活跃阶段高利用率，但没有算子时间线 | 依据 trace 改 launch、访存或数据布局 | CUDA、Nsight、算子性能分析 | 不能由 GPU 利用率直接推导改进点 |

## 1. 端到端亲和性校准：从人工配置走到可复现的自动选择

相关源码：`tools/calibrate.py` 的 `measure()`、`worker_candidates()`、`pick()`；`strata_control/calibration.py`；`src/program/generate.cpp` 的 `measure_pool_affinity()`。

已有能力不能重新包装成原创：

- 引擎已有 `--pool-affinity p-cores`、`all`、`measure`。已关闭的 [PR #1912](https://github.com/Niko1221/Strata/pull/1912) 实现了启动时专家微基准的布局选择。
- Python 校准器已根据 CPU 拓扑增加工作线程数候选，并已有 PCIe/MTP 交替确认；不是完全没有混合核支持。
- [Issue #3262](https://github.com/Niko1221/Strata/issues/3262) 报告 Linux LP-E 分类问题，设备和系统不同，本机不能验证其修复。

静态检查发现的候选空间：Python 的 worker 步骤修改 `--pool-workers`，没有将 `--pool-affinity` 作为联合候选；每个线程数仅一次启动、两次测量，随后 `pick()` 比较中位数，缺少该阶段自己的多次重启交替确认。需要实验确认它是否会错选，不能据代码直接宣布 bug。

可做的一项聚焦改动：在用户显式运行校准时，增加 all / p-cores 布局候选，用端到端 decode 验证引擎微基准的选择；只在稳定超过门槛时保存设置，不改普通启动默认。另一个独立选题是仅修复 worker 候选确认方式，避免一次启动的漂移被保存为优化。两项不要硬塞成一个 PR。

实验应区分两个问题：

1. CPU 布局本身的作用：固定实际 expert slots/字节、上下文、KV、草稿、PCIe 分配和提示；记录实际线程放置。相同 worker 数不保证相同布局。
2. 产品整体配置的作用：允许 auto 缓存随布局变化，比较最终用户体验；明确收益包含缓存分配差异。

至少 5 组交替重启配对，覆盖代码、中文、英文，以及预填充负向检查。使用相同构建、相同模型和采样；报告每组结果而不只报告最大值。采用门槛可沿用现有 3%，另要求配对结果稳定；补充回答正确性检查。启动耗时、取消、候选启动失败、已有配置保留和非混合 CPU 是必要边界。

原有三组 P 核结果是选题依据，不得描述成“新增校准器带来 12% 加速”。新补丁需要自己的实验，检查是否能稳定选到更好的布局。

## 2. 多会话缓存：优先优化重复工作，而非重复工作中的算子

相关源码：`serve/server.py` 的 prefix/checkpoint 参数和会话处理；`src/program/generate.cpp` 的 conversation cache；参考 `docs/DETAILS.md` 多会话说明。

上游 [Issue #3493](https://github.com/Niko1221/Strata/issues/3493) 附上 Deepseek Harness 的 12 条请求，均显示 Reused=0。仅凭日志不能确认是模板不稳定、会话交错、检查点失效还是客户端行为，不能宣称找到其根因。

本机探针：`flash-next/probe_prefix_reuse.py`，原始响应 `flash-next/prefix-reuse-probe.json`，使用合成文档和唯一标签，不重启服务，不更改配置。一次执行结果：

| 请求 | 提示 token | 缓存 token | 引擎 prompt_ms |
| --- | ---: | ---: | ---: |
| A 首次 | 2886 | 0 | 5711.0 |
| A 原样重复 | 2886 | 2879 | 80.2 |
| 独立短会话 B | 47 | 0 | 643.3 |
| 返回 A | 2886 | 0 | 2998.0 |

这是功能观察，不是正式速度 A/B：引擎和 OS 已有缓存状态不同，每项一次，输出仅 2–3 token，不能用来评价解码速度，也不能把 5711/80 的比值当作新优化的加速比。只证明当前路径能连续复用，以及此交错序列没有保住 A。

当前 `--conversation-cache-mib` 默认为 0。已有 RAM 停车缓存、slot 限制、最短提示长度、最小 park gain 和可用内存下限；`setup.py` 也已有给多 Agent 用户的启用提示。**不能重复提交“实现多会话缓存”**，本次行为也不能直接作为缺陷。

下一轮实验：

- 比较关闭/4 GiB/8 GiB 停车预算，先确定一份 4K/16K/32K 会话快照到底多大，预算太小的候选如实报告。
- A→A、A→B→A、A→B→C→A、长会话夹短请求四种工作负载；分别测试同一会话追加、原样重试、真实客户端工具调用序列。
- 记录 token 前缀相同长度、cached_tokens、TTFT、客户端总耗时、保存/恢复耗时、RAM 工作集和提交量峰值；将冷预填充与缓存恢复分开。
- 确认收益是否被每轮快照复制抵消；比较现有 min-tokens / park-gain 策略后，才决定是否需要代码改动。
- 只有复现错误驱逐、短请求污染或不必要快照写入时，才设计 opt-in 的策略改进。否则先贡献交错会话 benchmark 和已有配置的可复现证据。
- 正确性须检查不同会话不串状态、连续会话与重新完整预填充的数值/任务结果、取消和恢复失败；不能为了命中率复用错误状态。模型有递归状态，不能简单把普通 Transformer KV 前缀技巧直接照搬。

这是较强的展示题目：解释“为什么 Agent 响应慢”，通过状态复用减少重算，同时量化 RAM、复制代价与尾延迟，而不只给显卡 tok/s。

## 3. PLE：发挥 128 GB RAM，但先确认磁盘是否在关键路径

相关源码：`src/ngram/ple_reader.cpp`、`include/strata/ngram/ple_reader.hpp`、`src/program/generate.cpp` 的 `ple_direct_rows_per_s()` 和 PLE 初始化。

[Issue #1425](https://github.com/Niko1221/Strata/issues/1425) 报告过 Windows direct 随机读取远低于 SSD 顺序带宽的现象。当前源码已实现 direct/mmap/ram 模式、并发读取和启动探测，不应把旧报告视为当前版本未修复的证明。

先测 direct / mmap / ram 与 inflight 的现有能力，使用真实多样文本，而不只用重复 filler（重复 n-gram 会低估 I/O）。采集 PLE 读取耗时占比、行数/唯一行数、命中率、磁盘延迟、实际 GPU 空隙和总 TTFT。RAM 模式的实际驻留和锁页是否成功必须看日志，不把参数名字当作成功证据。

如果读取占主导，再看 batch 内已有去重/排序是否足够、重复行能否避免 I/O、并发深度是否超过 SSD 最佳点。先读现有实现避免重复。改动前先就已有 issue 商定范围。

## 4. CPU/CUDA 深入路线

AVX2：当前文档已描述 `STRATA_CPU_IQ_ALL_EXACT1=1` 的精确单 token IQ3_S 路径，其他机器微内核明显改善但端到端未达 3%。本机可验证其收益，不能把既有内核当作新实现。用 `src/kernels/cpu/native_expert.cpp` 的格式/组大小派发和现有 parity 工具定位，记录每窗口 CPU 时间与总窗口时间。即使某微内核快一倍，若关键路径占比 10%，理想总收益上限也仅约 5.3%（Amdahl），并且重叠会改变其关键路径贡献。

CUDA：建立 Nsight Systems 时间线区分专家上传、计算、CPU 等待；再用 Nsight Compute 分析占比高的具体 kernel。分别检验 launch 数量、带宽、访存合并、占用率与 CPU/GPU 同步，不能只追高 occupancy。先查 sm_120 已有专用路径和相应 PR，再决定一个算子级改动。

本轮 PATH 没发现 nvcc/cmake，仅找到 ninja；这不证明整机未安装 CUDA Toolkit 或编译器。原生实验前需检查安装目录和构建环境。修改共享原生文件时按贡献规则完成所有受影响后端构建；缺少环境的检查如实列出，不以预编译发布引擎验证冒充修改后的构建验证。

## 不建议现在优先做

- 再盲扫 PCIe/MTP 参数：本机已做过确认，PCIe 0.3 的初筛收益未复现，MTP 也无稳定胜者。
- 直接扩大显存缓存：当前只剩约 0.5 GiB，存在 WDDM 瞬时分配风险，不能只看空闲 RAM。
- 多 GPU、Linux LP-E、AMD 专用优化：本机无法验证这些硬件情形，不适合当前首个性能 PR。
- 宣称 NVFP4 必定优于 IQ3_S：同卡的 [Issue #3491](https://github.com/Niko1221/Strata/issues/3491) 使用不同 CPU、PCIe、量化及上下文，不能直接比较 tok/s。量化实验还需质量和总驻留成本。
- 只写“打开某个开关快了”：可作为 benchmark 贡献，但不足以证明原创调度或内核优化。

## 做成能讲清楚的作品

保留一个聚焦代码 PR，加一套公开合成 workload、固定版本/配置、原始测量、错误与取消测试，以及改前/改后时间线。讲述顺序：用户工作负载 → 瓶颈证据 → 假设 → 最小改动 → 排除混杂 → 正确性 → 收益与适用边界。

针对推理服务/系统岗位，先做多会话与自动调优；针对 CUDA/高性能计算岗位，再深入一个经 profiling 证实的 kernel。简历只能写实际完成并测量的内容，注明硬件和工作负载，不把计划、他人的实现或最佳单次结果写成自己的成果。PR 是否合并与个人能否解释每行代码同样重要。

本轮没有新建上游性能 issue/PR，没有更改日常配置或停止服务。方向确认前已经搜索 open/closed 讨论，但不是穷尽查重；实施前需再次核对最新上游。
